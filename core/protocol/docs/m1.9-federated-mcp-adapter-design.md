# M1.9 — Federated MCP Reference Adapter (Design)

**Status**: design — 2026-04-25
**Author**: gnanirahulnutakki
**Replaces**: nothing (new deliverable from `whitepaper-mcp-for-clusters.md` §7.2)

## Purpose

The current `core/adapters/k8sgetpods` proves the protocol shape against the
Kubernetes API. It does **not** prove the federation claim, because:

1. It does not speak MCP. It speaks the Kubernetes Go client. The whitepaper's
   central proposition is "MCP traffic crossing cluster boundaries"; the
   k8s-get-pods adapter is a typed-action proof-of-concept that happens to
   target K8s.
2. It runs in one cluster. There is no second cluster. The "federation" exists
   only at the abstraction layer; on the wire, gateway and agent are in the
   same VPC, often the same namespace.
3. There is no end-user identity propagation across a real trust boundary —
   the JWT validation path executes but only against a synthetic token.

M1.9 closes all three gaps with one self-contained deliverable: an MCP server
running in cluster A invoked by an agent in cluster B with a real end-user JWT,
real mTLS hops, real durable-queue dispatch, and a single canonical audit
record produced at the gateway.

## What gets built

### Component 1 — MCP server in cluster A

**Choice**: `github-mcp` (https://github.com/github/github-mcp-server) over
`postgres-mcp` because:

| | github-mcp | postgres-mcp |
|---|---|---|
| Public, maintained | Yes (Anthropic + GitHub) | Several forks; ownership unclear |
| Realistic federation use case | Yes — "agent in CI cluster needs to query GH issues from finance cluster" | Yes — "agent in inference cluster needs PG read in data cluster" |
| Auth complexity | GH PAT or OAuth | DB user/password or IAM RDS |
| Setup friction | Low (one PAT) | Medium (DB instance + schema) |
| Auditable result | Yes (issue/PR fetch is read-only, idempotent) | Yes |
| Tool surface | ~15 read tools | ~5 read tools |

`github-mcp` deploys as a Pod in cluster A. PAT comes from `vault://github-pat?scope=read`,
referenced in the federation envelope per §3.5. Agent dereferences locally.

### Component 2 — MCP client inside our agent

The agent today reads `OperationDispatch.PayloadDigest` and looks up an adapter
by `schema_uri`. M1.9 adds a new adapter family `mcp-client` that:

1. Decodes the envelope payload as an MCP `CallToolRequest` (JSON).
2. Connects to a local MCP server (cluster A) over the MCP transport
   (stdio for in-pod, HTTP-with-SSE for sidecar topology). Default: HTTP.
3. Sends the `tools/call` request, awaits result.
4. Wraps the MCP `CallToolResult` (or error) into an `OperationResult`
   with hash-chained agent evidence per §3.2.
5. Records an `attestation_quality` field — `agent-asserted` initially
   (the MCP server itself doesn't sign responses); `server-signed` when
   github-mcp grows that capability.

This is a Go package: `core/adapters/mcpclient/`. ~200-300 LOC.

### Component 3 — Two-cluster deployment manifests

`core/deploy/k8s/m1.9/`:

```
m1.9/
├── cluster-b-caller/
│   ├── agent.yaml           # federation agent dialing out to gateway
│   ├── agentgateway.yaml    # local single-cluster MCP gateway (Solo.io agentgateway or our sidecar)
│   ├── identity-mock.yaml   # small JWT issuer for the demo (real IdP in M2)
│   └── caller.yaml          # demo caller pod that issues `tools/call`
├── cluster-a-callee/
│   ├── agent.yaml           # federation agent in cluster A
│   ├── github-mcp.yaml      # github-mcp server Pod
│   ├── vault-stub.yaml      # K8s Secret containing GH PAT for now (real Vault in M2)
│   └── network-policy.yaml  # local egress allow only to GH API
└── gateway/
    ├── gateway.yaml         # central federation gateway
    ├── audit-store.yaml     # PostgreSQL or SQLite for audit
    └── policy.yaml          # OPA/CEL central policy ("allow only github-mcp/{issues,pulls}/list" for the demo identity)
```

The two clusters can be (1) two `kind` clusters on a developer laptop — the
default for `make m1.9-demo`; (2) two real EKS/GKE/AKS clusters for the
"in-the-wild" reproduction story.

### Component 4 — End-to-end test harness

`core/test/m1.9/e2e_test.go`:

1. **Setup**: brings up two `kind` clusters (`cluster-a`, `cluster-b`) via
   `kind create cluster`; deploys the manifests; waits for readiness.
2. **Identity**: issues a JWT for `user=demo@example.com` from the mock IdP.
3. **Call**: from cluster-b's caller pod, invoke MCP `tools/call` with
   `tool=github-mcp/list-issues, arguments={owner:..., repo:...}`.
4. **Verify** (these are the assertions that matter):
   - The result contains real GitHub issues data (PAT works, MCP server runs).
   - The audit store contains exactly **one** `AuditEvent` for the call.
   - That `AuditEvent` carries `actor.email=demo@example.com` (JWT propagated).
   - That `AuditEvent` carries `cluster_origin=cluster-b` and
     `cluster_target=cluster-a` (different SPIFFE IDs).
   - The PAT bytes never appear in the gateway's logs or audit store
     (credential boundary).
   - `attestation_quality=agent-asserted` (honest about what we know).
   - The local agent in cluster A has policy logs showing it evaluated
     a local policy before forwarding (dual policy works).
5. **Negative paths**:
   - Same call with a JWT for `user=denied@example.com` → 403, denial
     audit record, no MCP call to github-mcp.
   - Same call when network policy blocks egress → propagated MCP error
     wrapped in our `OperationResult`, audit record shows `outcome=failure`.
   - Same call with an expired JWT → 401, audit record, no dispatch.

The test must run in CI under `make ci-m1.9` in <5 minutes; if it cannot,
the manifests are too heavy and the demo isn't repeatable.

## What does *not* get built in M1.9

Explicitly out of scope, with the milestone they shift to:

- **Real Vault**: M2 (replaces `vault-stub` K8s Secret).
- **Real IdP**: M2 (replaces `identity-mock` with Keycloak or external OIDC).
- **Real CA**: M2 (replaces self-signed dev CA with cert-manager + Vault PKI per M1.4).
- **`server-signed` attestation**: depends on github-mcp itself signing
  responses; not on our roadmap, will be honest about `agent-asserted` quality.
- **Schema-trust enforcement**: M2 (this demo allow-lists exactly one
  `schema_uri = mcp://tools/call/v1.0`; full schema-trust per §3.1 is a
  separate milestone).
- **Conformance test cases**: M2 (this demo is a *single* end-to-end path,
  not a conformance suite).
- **Multi-tenant policy**: M2 (D17 multi-tenancy is a separate decision).
- **Persistent durable queue under crash**: M1.5 (running concurrently;
  M1.9 uses the SQLite default but does not specifically test crash-safety).

## Acceptance criteria

M1.9 is done when **all** of these hold:

- [ ] `make m1.9-demo` brings up two `kind` clusters, deploys manifests,
      runs the end-to-end test, and prints PASS in <5 minutes on a developer
      laptop with no network beyond GitHub API access.
- [ ] The recorded audit event for the happy-path call is reproducible —
      same input produces a record with the same shape (modulo timestamps
      and call_ids).
- [ ] The PAT bytes do not appear in any of: gateway stdout, gateway
      audit store, gateway log file, federation-agent stdout for cluster B
      (only cluster A's agent should ever see the dereferenced credential).
- [ ] An external reviewer who clones the repo can reproduce the demo
      following only the README — no undocumented setup steps.
- [ ] The whitepaper §7.1 ("What exists today") gains a paragraph
      describing the M1.9 demo with a link to the recorded session
      (asciinema or screencast).

## Build sequence

Suggested implementation order, biased toward fail-fast on the riskiest
parts first:

1. **MCP client in agent first** (fastest to validate the wire shape).
   Test: stand up github-mcp locally, point our agent at it directly
   (no federation), verify the round trip works. ~1 day.
2. **Two-cluster topology with kind**. No federation logic yet — just two
   `kind` clusters with a tunnel between them and a sanity check that
   pod-in-cluster-b can reach a service-in-cluster-a. ~0.5 day.
3. **Federation agent in cluster A dialing the gateway from inside that
   cluster**. Existing primitive; just deploy it. ~0.5 day.
4. **Wire up the central policy** to allow exactly the demo call.
   ~0.5 day.
5. **End-to-end happy path**. This is where bugs surface. ~1-2 days.
6. **Identity model**: mock IdP, JWT minting, propagation through envelope,
   validation at every hop, audit-record actor field. ~1 day.
7. **Negative paths and audit invariants**. ~1 day.
8. **Documentation pass**: README walkthrough, recorded demo,
   whitepaper §7.1 update. ~0.5 day.

Total: 6-8 days of focused work. Multi-CLI orchestration via `/ai-dev-team`
can compress this — codex for the agent's MCP client (Go, security-sensitive),
gemini for the manifest generation (mechanical, large), cursor-agent for the
test harness.

## Risk register

- **github-mcp may break or change shape** — mitigation: pin to a specific
  release tag, document the version, abstract the MCP-client adapter so
  switching MCP servers is a config change.
- **kind clusters' inter-cluster networking is fiddly** — mitigation: provide
  a `docker compose` fallback that wires two single-cluster setups via
  a docker network (loses K8s realism but keeps the protocol path real).
- **JWT validation across mock IdPs is fiddly** — mitigation: use an
  off-the-shelf IdP container (e.g., `quay.io/keycloak/keycloak:25` or a
  minimal Go OIDC stub), don't roll our own.
- **The audit-event shape may need a v0.2 envelope field for
  `attestation_quality`** — mitigation: add the field as an optional
  string in the v0.1 envelope; non-breaking; document the values.
- **External reviewer can't reproduce** because of laptop differences —
  mitigation: pin all container image digests, document
  CPU/memory minimums, add a `make m1.9-doctor` to diagnose missing
  prereqs.

## Why this matters for the whitepaper

The whitepaper §7.1 (post-revision) explicitly downgrades the current state
to "prototype evidence." M1.9 is the deliverable that lets the next revision
of §7.1 honestly say:

> An end-to-end MCP federation demonstration ships with the repo. The
> github-mcp server runs in cluster A; an agent in cluster B invokes
> `tools/call` against it via the federation gateway with a real end-user
> JWT propagated through the envelope. Audit records are produced at the
> gateway with full identity and policy context. The demo runs reproducibly
> on two `kind` clusters in under five minutes. See `core/deploy/k8s/m1.9/`
> and the recorded session at [link].

That is the difference between "we have a sketch" and "we have something
external reviewers can poke at." It is the prerequisite for any
TAG-AI / CNAIWG submission, and it is the prerequisite for the
adoption-signal conversation.
