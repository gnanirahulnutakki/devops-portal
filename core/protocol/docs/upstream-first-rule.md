For the B→A path to work, “upstream-first” cannot be a slogan. It has to be an operating rule that survives the eventual split. In this repository, “upstream” means the `core/` submodule: protocol, reference agent, reference gateway, conformance, and the documentation that defines them. It must be treated as if it already lived in a standalone CNCF repository. “Downstream” means the Radiant product code outside `core/`, especially `src/`, `app/`, and `prisma/`.

The rule is strict: all protocol and reference-implementation changes happen upstream first. Downstream consumes only released upstream versions, pinned by semver. Downstream is not allowed to consume unpublished protocol fields, import from non-public upstream interfaces, depend on pre-release adapter semantics, or reach into `core/` internal packages. If downstream needs a feature that upstream does not yet expose, downstream waits or helps land it upstream.

The feature process is linear. Open an upstream issue. Write the design. Merge the upstream PR. Cut an upstream release. Update downstream to the new version. No exceptions. If the team violates this once “just to move faster,” the split is already compromised.

This matters because M6 is a mechanical extraction, not a rewrite. The plan is `git subtree split core/ --branch split-core` into a standalone repository. If downstream has been reaching into private upstream symbols or using unpublished wire fields, the split breaks both halves at once: the new standalone repo is incomplete, and the downstream product loses hidden dependencies it was never supposed to have. That is avoidable only if `core/` is treated as a public product boundary from the first commit.
