This protocol uses dual policy placement because a single decision point is insufficient. A gateway-only policy engine can answer who is allowed to ask for something, but it cannot reliably answer whether the concrete local execution context is still safe by the time the agent touches the target. An agent-only policy engine has the opposite problem: it sees local truth but cannot authoritatively decide central scope, operator entitlement, or time-window constraints.

The central decision runs at the gateway. It answers admission questions: is this operator or machine principal allowed to invoke this adapter, against this cluster or tenant set, during this time window, under this change context? This is the policy that determines whether a request is admitted into the protocol at all. If the central decision is `DENY`, the request never leaves the gateway.

The local decision runs at the agent. It answers execution-time questions: does the target namespace still exist, is the workload in the expected state, does this adapter’s local invariant still hold, is the local environment missing a prerequisite, or has the local policy bundle narrowed the allowed action since the request was issued? OPA’s deployment guidance is explicit that policy decision points should run close to the enforcement point when latency and reliability matter ([OPA deployment guidance](https://www.openpolicyagent.org/docs/deployments)). This is exactly that case.

Both decisions are emitted to audit. `AuditEvent` carries `central_verdict` and `local_verdict` because “allowed centrally but denied locally” is operationally and forensically different from “denied centrally and never sent.” The protocol standardizes that envelope so downstream tools do not invent incompatible audit stories.

The policy engine is not the project. OPA and CEL already exist, and they already cover the decision-language problem. Gatekeeper and Kyverno already own Kubernetes admission, mutation, generation, and policy reporting. This protocol is not replacing them. The distinct layer here is the operation-scoped envelope: typed request schema, optional approval chain, central and local placement, and a standardized auditable verdict record. That is the missing interoperability layer.

Failure behavior is strict. If the central decision denies, the request is not dispatched. If the local decision denies, the request may arrive at the agent for evaluation, but it is never dispatched to the adapter and it never reaches `RUNNING`. In both cases, an `AuditEvent` records the denial. “Denied but invisible” is forbidden.
